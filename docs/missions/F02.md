## Remise au parent : exécution distante uniquement

F02 est **prêt pour exécution distante et revue**, pas validé. Les commandes
ci-dessous ne sont pas exécutées par cet agent. Le parent identifie le moteur
Docker de test, vérifie espace/RAM, absence totale de ports publiés,

réutiliser un projet existant. Le harness F01 n'est ni remplacé ni redéployé.

Créer le contexte de build à partir de `git archive <SHA-F02>` dans un répertoire
de test distant neuf : uniquement les fichiers suivis, aucune `.env`, `.git`,
venv/cache ou donnée utilisateur envoyée au builder. Fournir les secrets via
un fichier externe au contexte, permissions restreintes. Les `COPY` Docker
incluent seulement le lock, pyproject, app et tests (stage test seulement).
Le runtime est non-root, read-only via Compose, deux workers, pas de migration
automatique, pas de confiance dans les en-têtes proxy. Wheels binaires requis ;
le build échoue si une dépendance native nécessite une compilation.

Exemple Bash à adapter par le parent **après vérification de la cible** :

```bash
# Le fichier externe reprend .env.example avec secrets aléatoires dédiés,
# APP_ENVIRONMENT=test et POSTGRES_DB=app_test (suffixe _test obligatoire).
# FIXER ces deux chemins/identifiants à la cible neuve vérifiée.
export F02_ENV_FILE=/chemin/test-isole/f02.env
export F02_PROJECT=nianzeuhub-f02-IDENTIFIANT-UNIQUE
dc() {
  docker compose --env-file "$F02_ENV_FILE" -p "$F02_PROJECT" \
    -f docker-compose.yml -f tests/infra/compose.remote.yml "$@"
}
dc --profile test config --quiet
dc --profile test config --format json | python3 tests/infra/check_remote_config.py
dc --profile test build --no-cache
dc up -d --wait api
dc ps -a
dc run --rm --no-deps tests python -c 'import av; print(av.__version__)'
dc run --rm --no-deps tests ruff check --no-cache .
dc run --rm --no-deps tests mypy --cache-dir=/tmp/mypy app
dc run --rm --no-deps tests
dc run --rm --no-deps core-tests
# Initialisation répétée : aucun objet supprimé, buckets toujours privés.
dc run --rm --no-deps buckets
dc run --rm --no-deps tests

# Pannes réelles, chacune suivie d'une remise en route même si la sonde échoue.
for dependency in db minio; do
  dc stop "$dependency" || exit 1
  dc run --rm --no-deps tests python tests/infra/probe_health.py unavailable
  probe_result=$?
  dc start "$dependency" || exit 1
  test "$probe_result" = 0 || exit "$probe_result"
  dc run --rm --no-deps tests python tests/infra/probe_health.py ready || exit 1
done

# Même UUID pour les trois phases ; conserver sa valeur dans la preuve QA.
export F02_PROBE_ID=$(python3 -c 'import uuid; print(uuid.uuid4())')
dc run --rm --no-deps -e F02_PROBE_ID tests python tests/infra/persistence.py seed
dc restart db minio
dc run --rm --no-deps tests python tests/infra/probe_health.py ready
dc run --rm --no-deps -e F02_PROBE_ID tests python tests/infra/persistence.py verify
# Recréation prouve aussi que les données ne vivent pas dans la couche conteneur.
dc up -d --no-deps --force-recreate --wait db minio
dc run --rm --no-deps tests python tests/infra/probe_health.py ready
dc run --rm --no-deps -e F02_PROBE_ID tests python tests/infra/persistence.py verify
dc run --rm --no-deps -e F02_PROBE_ID tests python tests/infra/persistence.py clean
dc run --rm --no-deps core-tests
```

Exécuter les commandes séquentiellement et arrêter au premier échec (hors reprise
explicite de la dépendance dans la boucle). Conserver SHA, versions, sorties et
codes de sortie. Aucun `down -v` ni effacement de volume. `clean` retire uniquement
la ligne UUID et les deux objets de la sonde ; schéma `f02_infra_probe` et table
de test restent sur les volumes dédiés. Le bootstrap applicatif n'écrit aucune
table : ce DDL est exclusivement dans la sonde de test explicitement invoquée.

`tests` utilise le réseau Compose pour rester utilisable pendant l'arrêt DB.
`core-tests` partage le namespace réseau DB pour respecter la garde F01

ne constituent pas une validation. Dans le protocole ci-dessus, ils doivent
